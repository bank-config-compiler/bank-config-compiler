# 项目价值评估

## Status

Accepted as project positioning assessment.

## Date

2026-05-27

## Context

本项目处于建设方向讨论阶段。`tmp/` 下已有一组未经确认、未经充分讨论的草案文档，提出了一个围绕银行接口文档解析、人工 Review、SchemaIR 和 Import JSON 生成的 MVP 构想。

本文件不确认具体技术方案、接口设计或实施计划，只沉淀当前已认可的第三方价值判断，用于后续讨论时校准项目定位。

## Assessment

从第三方视角看，该项目具备明确业务价值，但价值不在于“自动化替代人工配置”，而在于“把高经验依赖的人工配置过程产品化、可审计化、半自动化”。

银企直连场景中的银行接口文档通常格式不统一，字段层级、必输规则、重复节点、条件说明和报文示例需要实施人员反复对照。现有工作强依赖经验，交付周期长，质量也受人员理解能力影响。该项目如果定位准确，可以把这些隐性人工步骤拆解成可查看、可编辑、可校验、可追溯的中间产物。

因此，该项目值得做 MVP。MVP 的目标应是验证“AI 能否辅助生成可 Review 的配置草稿”，而不是宣称“自动生成生产可用银行配置”。

## Core Value

### 降低实施起步成本

系统即使只能生成 70% 到 80% 可用的草稿，也可能显著减少从零阅读文档、整理字段、识别层级和转换配置的时间。

### 沉淀可复用流程

DocIR、SchemaIR、Validator、Rule Engine 这类中间链路的价值在于把专家脑内步骤显性化。相比直接让 LLM 生成最终 JSON，这种方式更容易持续改进，也更适合团队协作。

### 提升质量可审计性

如果每个字段都能保留来源文本、置信度、不确定标记、Review 记录和校验结果，后续排查问题时就能追溯字段从哪里来、谁确认过、规则如何转换。这一点对银行和企业集成场景尤其重要。

### 为后续自动化打基础

如果 SchemaIR 设计合理，未来不仅可以生成 Import JSON，也可以扩展到 DTO、Mock、Diff、字段映射、测试用例和配置变更对比等能力。

## Suitable Positioning

该项目适合作为：

- 银企直连实施工具
- 银行接口配置辅助工具
- 内部交付提效平台
- 配置草稿生成与 Review 平台

该项目不应在早期定位为：

- 全自动银行接口配置生成器
- 无需人工校验的生产配置系统
- 通用文档理解平台
- 多银行、多标准、全格式自动解析系统

## Key Risks

### LLM 抽取质量不稳定

银行接口文档常见表格错位、嵌套层级不清、条件规则散落、字段表与示例不一致等问题。LLM 可以辅助理解和整理，但不能作为最终可信源。

### Import JSON 真实格式不明确

如果最终 Import JSON 只是示例格式，而不接近真实银企直连配置模型，MVP 只能证明链路能跑，不能证明能减少真实实施成本。

### 范围容易膨胀

PDF、OCR、bbox 高亮、多用户审批、RAG、多 Agent、规则学习等能力都可能把项目拖成平台工程。MVP 阶段需要克制范围。

### 中间表示决定上限

DocIR 和 SchemaIR 如果过于随意，后续难以复用；如果一开始设计过重，又会拖慢 MVP。中间表示需要服务于当前验证目标，同时保留必要的可追溯字段。

## Value Boundary

该项目成立的前提是坚持 Human-in-the-loop 和确定性 Rule Engine，不把 LLM 输出直接包装成可信配置。

第一阶段如果能证明以下事实，项目就具备继续建设价值：

- 能处理一份真实或接近真实的银行接口文档。
- 能自动生成可读 DocIR。
- 人工能快速修正 DocIR。
- SchemaIR 能覆盖关键字段，并保留来源证据。
- Validator 能拦截明显错误。
- Rule Engine 能稳定生成接近真实导入结构的 Import JSON。

如果 MVP 最终只是让 LLM 读取一段样例文本并生成演示 JSON，那么价值有限，更多是技术展示，不足以支撑系统化建设。
